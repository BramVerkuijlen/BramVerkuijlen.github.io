Monitoring Expansion : API

Created by Bram Verkuijlen, last modified on dec 19, 2025

OpenText Content Server (OTCM) does not provide dedicated metrics endpoints like a Prometheus exporter. However, its REST API exposes multiple routes whose responses contain structured data that can be used for both performance and business monitoring.

By periodically polling these endpoints, you can gather:

  • Business metrics – Operational usage of the system, e.g., number of active workflows, ongoing WebReports, document volumes. These indicate workload trends, process throughput, and resource usage.

  • Performance metrics – Response times, error rates, subsystem availability, and latency indicators. These help identify bottlenecks and capacity issues.

This approach enables a single API-based workflow to monitor both functional usage and technical performance.

For a complete reference of all OpenText Content Server (OTCM) API calls, see the official documentation.

Key Endpoints & Descriptions

System Health Checks - /v2/systemhealth

  • Provides lists of health test groups and detailed test results.

  • Can be used as a primary source for early warning of system degradation.

Bruikbare metrics:

Metric

Description / Use

test_success / test_warning / test_fail

Health status of individual components

test_total

Total checks, baseline for monitoring

duration / time_started

Execution time per test, useful as performance proxy

error_message / state

Event-style indicators of issues

Example:

  • test_warning > 0 → early warning for subsystem degradation

  • duration fluctuation → potential latency or performance issues

  • test_fail > 0 → hard failure requiring attention

Workflow Metrics - /v2/workflows/status/processes/{process_id}

  • Workflows represent operational process flows, suitable for both business and load monitoring.

Bruikbare metrics:

Metric

Description / Use

Number of workflow activities

Number of actions within workflows (load indicator)

Distribution of actions (approve, reject, route)

Operational trends and usage patterns

Activities per user

User activity levels

Event timestamps

Step-level duration for performance tracking

Document types / mimetypes in actions

Insights into types of processed content

Example:

  • Active workflows at a given time

  • Actions per workflow type per day

  • Average time between workflow steps

Additional API Opportunities

  • Node & Content endpoints – Number of documents, object type growth, volume trends, mime type distribution. Useful for capacity and volume metrics.

  • Audit & Event APIs – Frequency of user actions, failed operations, unusual patterns. Event rates indicate system load.

  • Search & Indexing endpoints – Response sizes, hit counts, indexing status/lag. Useful for search performance and latency monitoring.

  • Member & User endpoints – Number of users, groups, roles, or changes over time. Useful for organizational or security metrics.

  • Admin & Configuration APIs – Availability of subsystems, configuration errors, upgrade statuses. Serves as system health indicators.

These endpoints are not explicitly designed for metrics, but periodic polling or log extraction can transform them into actionable business and technical insights.

Observability Context

  • API-derived metrics complement logs and system monitoring events.

  • Enables correlation between business usage trends and system performance indicators.

  • Particularly useful in environments where direct Prometheus-style exporters are not available.
