Monitoring Expansion : Distributed setup

Created by Bram Verkuijlen, last modified on dec 29, 2025

This page describes how the components of the Monitoring Expansion Proof of Concept (POC) could be deployed in a distributed environment.

The purpose of this page is not to describe an implemented setup, but to document:

  • Which components support distributed deployment

  • Which technologies could be used

  • Why distributed deployment was out of scope for this POC

This page is based on architectural analysis and established deployment patterns of the used technologies, and NOT on practical implementation or validation performed during this project.

Overview

The Monitoring Expansion POC was intentionally designed and tested as a single-host, Windows-based setup.

This aligns with the project goal:

To explore what monitoring data can realistically be gathered from a Windows-based enterprise ECM system (OpenText Content Management Server V24.4).

While all components support distributed deployment, this was not required to validate the monitoring possibilities of xECM.

Distributed Deployment Possibilities

Most components used in the POC are designed to run independently and can be deployed in distributed environments.

Components with Native Distributed Support

The following components support independent or distributed deployment:

OpenTelemetry Collectors

  • Can run as standalone services

  • Can be scaled horizontally

  • Commonly deployed in containerized environments

Prometheus

  • Can scrape remote targets

  • Supports federation and remote storage

Loki

  • Supports single-node and distributed modes

  • Commonly deployed using containers or Kubernetes

Grafana

  • Designed to run independently

  • Can connect to remote Prometheus and Loki instances

Fluent Bit

Fluent Bit is typically deployed close to the source system.

In this POC:

  • Fluent Bit runs on the same Windows host as xECM

  • This minimizes network dependency and complexity

In distributed setups:

  • Fluent Bit is usually deployed as:

    • A sidecar

    • A daemonset

    • A local agent per host

Supported Deployment Models (Conceptual)

The following deployment models are technically possible but were not implemented:

Containerized deployment

  • Docker

  • Kubernetes

Multi-host deployment

Separate servers for:

  • Collectors

  • Prometheus

  • Loki

  • Grafana

Hybrid setups

  • Windows-based xECM

  • Linux-based observability stack

These models are commonly used in cloud-native environments but were out of scope for this POC.

Why Distributed Deployment Was Out of Scope

Distributed deployment was intentionally excluded for the following reasons:

  • The primary research focus was data availability, not infrastructure scalability

  • xECM is deployed on Windows, not containerized platforms

Introducing distributed complexity would:

  • Increase setup time

  • Reduce focus on observability research

  • Provide limited additional insight for the project goals

The POC aims to answer:

What data can we observe from xECM on Windows?

—not:

How do we run a large-scale observability platform?

Linux Considerations (Out of Scope)

Some observability tooling, particularly OpenTelemetry, is more mature on Linux-based systems.

Potential (untested) advantages include:

  • Better support for containerized deployments

  • Additional OpenTelemetry receivers and processors

  • Potential use of Java agents for application-level instrumentation

However:

  • No testing or validation was performed

  • Results cannot be confirmed or documented reliably

Linux-based observability for xECM is therefore considered future research and not part of this POC.
