Purpose

Early in the project, agent-based instrumentation was investigated as a potential way to integrate OpenTelemetry directly into OpenText Content Management Server (OTCM).

The goal of this research was to determine whether the OpenTelemetry Java Agent could be attached to the OTCM runtime in order to:

  • Automatically capture JVM metrics

  • Generate distributed traces

  • Collect application-level performance data with minimal configuration (“zero-code instrumentation”)

This approach would align with modern observability best practices and could potentially integrate OTCM directly into AmeXio’s existing monitoring landscape.

Initial Assumptions

At the start of the research, the following assumptions were made:

  • OTCM runs on the Java Virtual Machine (JVM)

  • OTCM could be treated as a standard Java application

  • A Java agent could be injected at startup or attached dynamically

  • OpenTelemetry Java Agent would be compatible with OTCM’s runtime

These assumptions are common when working with Java-based enterprise applications, but later proved to be partially incorrect in the context of OTCM.

Technical Context

System Environment

  • OTCM Version: 24.4

  • Operating System: Windows Server

  • Execution Model: Windows Service (llserver.exe)

  • JVM Version: Java 11.0.17

  • Java Agent: opentelemetry-javaagent.jar

  • Agent Version: 2.20.1

OpenTelemetry Java Agent

  • Provides zero-code instrumentation for Java applications

  • Designed to be attached using:

    • JVM startup options (-javaagent)

    • Environment variables (JAVA_TOOL_OPTIONS)

    • Dynamic attachment tools (e.g. jattach)

Experiments and Attempts

1. JVM Startup Injection via opentext.ini

The first approach was to preload the OpenTelemetry agent by modifying the OTCM JVM options located in the opentext.ini.

Configuration attempt:

[javaserver]
JavaVMLibraryPath=.\jre\bin\server\

# OpenTelemetry Agent
JavaVMOption_1=-javaagent:"C:\OTel\opentelemetry-javaagent.jar"
JavaVMOption_2=-Dotel.javaagent.debug=true
JavaVMOption_3=-Dotel.service.name=OTCM-Test

# OTCM defaults
JavaVMOption_4=-Djava.class.path=.\ojlib\fileprefs.jar;.\ojlib\classloader.jar
JavaVMOption_5=-Xrs
JavaVMOption_6=-Djava.system.class.loader=com.opentext.livelink.oj.LivelinkClassLoader
JavaVMOption_7=-Djava.util.logging.config.file=C:\OPENTEXT\OTCS\config\javaserver.logging.properties

Outcome:

  • OTCM Windows service (llserver.exe) started and stopped imidiately after

  • OTCM web interface was not accessible

  • No agent logs were generated

  • No errors appeared in standard OTCM logging

2. Environment Variable Injection (JAVA_TOOL_OPTIONS)

A second attempt was made using the JAVA_TOOL_OPTIONS environment variable, which is commonly used to inject Java agents without modifying startup scripts.

Outcome:

  • Environment variable was correctly set

  • OTCM did not pick up the agent

  • No observable change in runtime behavior

3. Dynamic Agent Attachment

Dynamic attachment using tools such as jattach was attempted to inject the agent into a running process, Windows unforionately does not support jattach.

Root Cause Analysis

After testing and consultation, a critical clarification was received:

Although OTCM uses a Java Virtual Machine internally, OTCM itself is not a Java process.

Key implications:

  • OTCM runs as a native Windows service

  • Java is embedded and controlled internally

  • The JVM lifecycle is tightly managed by OTCM

  • External Java agents are not supported or expected

This invalidates the core assumption required for agent-based instrumentation.

External Expert Feedback and Clarification

During the early research phase, the findings and assumptions regarding agent-based instrumentation were shared with external experts who have experience working with OpenText Content Management environments, including individuals involved in third-party management and monitoring solutions for OTCM.

Key Clarification

An important clarification received was the following:

Although OTCM uses the Java Virtual Machine to execute certain components, OTCM itself is not a Java process.

This distinction has significant architectural implications:

  • OTCM runs primarily as a native Windows service (llserver.exe)

  • Java is embedded and invoked internally rather than acting as the primary application runtime

  • The JVM lifecycle is managed entirely by OTCM

  • External Java agent injection is not part of the supported execution model

As a result, assumptions typically valid for Java-based applications do not directly apply to OTCM.

Supported and Common Monitoring Approaches in Practice

Based on experience shared by external experts working with OTCM environments, the following approaches are commonly used and supported:

REST API-Based Monitoring

OTCM exposes a limited set of REST API endpoints that can be used for basic availability and health checks, including:

  • /v1/ping

  • /v2/systemhealth

These endpoints are suitable for uptime monitoring and coarse-grained health validation.

Log-Based Observability

Log aggregation is a widely adopted and supported strategy for monitoring OTCM:

  • OTCM produces detailed logs covering:

    • Request handling

    • Security and authentication

    • Database and web activity

    • Timing and thread execution

  • Log shipping to external systems is common practice

  • OpenText cloud deployments explicitly support Fluent Bit as a log shipper

With sufficient logging enabled, it is possible to achieve:

  • Request-level visibility

  • Performance analysis

  • Error detection

  • Partial trace reconstruction

Internal Metrics and Third-Party Tooling

OTCM also maintains internal performance and timing metrics related to:

  • Thread activity

  • Execution timing

  • Resource usage

While these metrics are not easily consumable in raw form, specialized third-party tooling (such as Fuse Management Central https://www.vilt-group.com/en/fuse) can expose and visualize this internal data in a more accessible way.

Clarification on OpenText Involvement

The document outlining the agent-based instrumentation approach was prepared as part of this research and shared with OpenText to request clarification on:

  • Official support for Java agents

  • JVM compatibility

  • Recommended observability strategies

At the time of this POC, no official confirmation or endorsement of agent-based OpenTelemetry instrumentation for OTCM was received from OpenText.

Therefore, architectural decisions within this project are based on:

  • Practical experimentation

  • External expert insight

  • Observed system behavior

  • Supported and documented OTCM capabilities

Conclusion

Based on experimentation and expert feedback:

  • Agent-based OpenTelemetry instrumentation is not feasible for OTCM in this context

  • The execution model of OTCM does not align with standard Java agent assumptions

  • Log-based and API-based observability approaches are more reliable and better aligned with supported practices

This conclusion directly influenced the final architecture of the Proof of Concept and the decision to focus on log-driven and indirect observability methods.

Impact on the POC Architecture

The outcome of this research directly shaped the final design of the POC:

  • Shift from agent-based instrumentation to log-based observability

  • Adoption of Fluent Bit as the primary ingestion mechanism

  • Use of OpenTelemetry Collectors for enrichment and transformation

  • Focus on metrics derived from logs and APIs

  • Tracing explored conceptually, not implemented

This reflects a realistic and production-aligned approach for enterprise ECM systems.
