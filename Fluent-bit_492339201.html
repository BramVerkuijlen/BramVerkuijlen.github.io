Monitoring Expansion : Fluent-bit

Created by Bram Verkuijlen, last modified on dec 19, 2025

OTCM does not provide native support for remote log shipping. To enable centralized collection and processing of logs, Fluent Bit is used as a lightweight log shipper.

Overview

Fluent Bit provides the following functionality for the POC:

  • Reads relevant OpenText Content management log files directly from the Windows VM (thread timing logs, client logs, SQL logs, security logs, Java logs).

  • Forwards logs to the OpenTelemetry Collector.
    Fluent Bit Logs Collector

  • Exposes a local HTTP input endpoint to receive system monitoring events pushed by OTCM.
    System Monitoring (JSON Events)

  • Supports basic log processing such as filtering, parsing, and tagging.

Why Fluent Bit?

  • Lightweight and efficient.

  • Compatible with OTCM’s log files.

  • Allows modular configuration via classic .conf files.

  • Can be replaced by OpenTelemetry Collector in the future if needed.

Modular Configuration Overview

Fluent Bit configurations are split across multiple .conf files using the @INCLUDE directive. This provides:

  • Modify, enrich, or filter logs between input and output.

  • Examples: add metadata, normalize timestamps, filter by severity.

  • Applied selectively using tags.

Official documentation on using @INCLUDE
https://docs.fluentbit.io/manual/administration/configuring-fluent-bit/yaml/includes-section

Example Main Configuration

[SERVICE]
    # Flush interval (seconds)
    flush        1

# Run in foreground (Off) or background (On)
daemon       Off

# Verbosity: error, warning, info, debug, trace
log_level    info

# Optional config files
parsers_file parsers.conf
plugins_file plugins.conf

# HTTP metrics server
http_server  Off
http_listen  0.0.0.0
http_port    2020

# Storage metrics <https://docs.fluentbit.io/manual/administration/buffering-and-storage>
storage.metrics on.

Inputs

@INCLUDE inputs/ot_monitoring.conf
@INCLUDE inputs/ot_security_logs.conf
@INCLUDE inputs/ot_timing_thread_logs.conf
@INCLUDE inputs/ot_timing_ctl_logs.conf

Output

@INCLUDE outputs/stdout.conf
@INCLUDE outputs/otlp.conf

Inputs (@INCLUDE inputs/*.conf)

  • Define log sources Fluent Bit reads (thread logs, security logs, system monitoring).

  • Each input config references the log type and optionally the parser.

  • Modular inclusion allows enabling/disabling log streams.

https://docs.fluentbit.io/manual/data-pipeline/inputs

Outputs (@INCLUDE outputs/*.conf)

  • Define where Fluent Bit sends logs (console, OTLP, HTTP, etc.).

  • Can match on tags to forward only specific log streams.

  • Modular outputs allow adding new destinations without changing main config.

https://docs.fluentbit.io/manual/data-pipeline/outputs

Parsers

  • Used to convert raw logs into structured data (JSON, key/value).

  • Parsers can be stored in a separate file (parsers.conf) and referenced in inputs.

  • Supports regex, JSON, and other formats for flexibility.

https://docs.fluentbit.io/manual/data-pipeline/parsers

Filters

  • Modify, enrich, or filter logs between input and output.

  • Examples: add metadata, normalize timestamps, filter by severity.

  • Applied selectively using tags.

https://docs.fluentbit.io/manual/data-pipeline/filters

Benefits of Modular Approach

  • Easier maintenance and readability.

  • Enables selective log collection.

  • Allows independent testing of inputs/outputs.

  • Supports future expansion or replacement with OpenTelemetry Collector.

Notes

  • Lightweight choice: Fluent Bit was chosen for its efficiency and ease of OTCM integration.

  • Future replacement: OpenTelemetry Collector could potentially replace Fluent Bit for more advanced observability needs.

  • Configuration: Classic .conf files were used to simplify modular management.

  • Logging coverage: Currently covers OTCM logs, system monitoring events, and optional filters for enrichment.
