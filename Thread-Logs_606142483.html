Purpose / Overview

Thread Logs record runtime activity of individual server threads within the OpenText Content Server.
They provide detailed insight into thread lifecycle events, functional execution, and runtime warnings or errors.

Unlike timing logs, Thread Logs are not primarily performance-focused, but they are extremely valuable for:

  • Functional troubleshooting

  • Error analysis

  • Understanding internal request handling and failures

While SQL executions are not logged directly, database-related issues (connection failures, timeouts, misconfigurations) often surface here as warnings or errors.

Relevance

Thread Logs provide detailed insight into the internal execution behavior of OpenText Content Server threads. While they are not performance-focused logs, they are a primary source for diagnosing functional and runtime issues when available.

Within this Proof of Concept, Thread Logs were not actively collected or centralized as part of the observability pipeline.

As a result, their relevance in this project is theoretical and architectural rather than validated through implementation. The documentation of Thread Logs is included to:

  • Provide completeness of OTCM logging capabilities

  • Explain their potential value in a production-grade monitoring setup

  • Highlight future opportunities for deeper troubleshooting and correlation

Correlation

Thread Logs are especially useful when correlated with other OTCM log sources:

  • Errors in Web Server Client Logs
    Web Server Client Timing Logs

  • Latency spikes in Thread Summary Timing Logs
    Thread Summary Timing Logs

  • Security or API-related failures

Observability Context

Thread Logs should be treated as a high-volume, high-detail diagnostic signal. Their effective use depends on:

  • Centralized collection

  • Severity-based filtering

  • Timestamp and thread-based correlation

Without filtering and correlation, raw Thread Logs quickly become noisy and difficult to interpret, reinforcing the need for a structured observability pipeline.

Monitoring & Metrics Potential

Although Thread Logs are unstructured, they can still be used to derive metrics such as:

Metric

Description

Error / warning rate

Stability and reliability indicator

Error type frequency

Identifies recurring configuration or API issues

Module-specific errors

Detects unstable components

Session-related failures

Authentication and session health

These metrics are commonly extracted using log parsing and aggregation (e.g. Fluent Bit → OpenTelemetry → Loki).
