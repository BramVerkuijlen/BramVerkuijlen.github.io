Monitoring Expansion : Performance monitoring

Created by Bram Verkuijlen, last modified on dec 30, 2025

This page documents recommendations for performance monitoring of OpenText Content Management Server (xECM), based on the findings of the Monitoring Expansion Proof of Concept (POC).

The recommendations in this section are partially validated through implementation in the POC and partially exploratory, reflecting architectural directions that could not be fully researched or implemented within the available timeframe.

Background

One of the key motivations for this project was the lack of performance visibility in the current AMI monitoring system. While availability and basic health metrics are present, detailed insight into application-level performance is largely missing.

During the POC, performance monitoring was therefore treated as a primary research focus. The goal was to determine:

  • What performance-related data xECM already exposes

  • How reliably that data can be collected

  • What gaps remain

Performance Monitoring in the POC

Log-Based Performance Metrics

The most reliable and detailed performance insights in the POC were obtained through existing xECM log files, specifically:

Web Server Client Timing Logs

Used to extract internal function and request timing metrics
Web Server Client Timing Logs

SQL Connect Logs

Used to extract database-related timing metrics
SQL Connect Logs

Using Fluent Bit and the Log Metrics Collector, these logs were successfully transformed into metrics representing:

  • Internal execution timings

  • Database call durations

  • Function-level performance characteristics

This approach provides valuable information on internal system behavior, especially when diagnosing performance issues.

API-Based Performance Metrics

The API Metrics Collector was used to measure:

  • API availability

  • Basic request duration metrics

While useful, this approach has limitations:

  • The collector must actively poll endpoints at fixed intervals

  • Measured timings are influenced by:

    • Network latency

    • Collector host performance

    • Scheduling intervals

  • Endpoints requiring authentication require:

    • A middleware layer, or

    • An API gateway capable of handling authentication

Additionally, only requests initiated by the collector itself are measured, meaning real user traffic is not directly observed.

Observed Limitations

Based on the POC findings, the following limitations were identified:

Log-based metrics provide deep internal insight, but:

  • Do not represent full end-to-end request lifecycle

  • Depend heavily on log quality and consistency

API-based checks:

  • Do not reflect real user behavior

  • Require polling, not passive observation

  • Become increasingly complex when authentication is required

Neither approach provides a complete view of:

  • Request lifecycle from ingress to response

  • System-wide performance under real load

Recommendation: Use the POC for Targeted Performance Analysis

The POC approach is best suited for:

  • Investigating specific performance issues

  • Understanding internal timing behavior

  • Supporting troubleshooting and root-cause analysis

It is recommended to use the POC:

  • During testing phases

  • When performance degradation is suspected

  • As a diagnostic tool alongside existing monitoring

The POC should not be treated as a full replacement for end-to-end performance monitoring.

Recommendation: Introduce a Reverse Proxy or API Gateway

For comprehensive performance monitoring, it is recommended to introduce a reverse proxy or API gateway in front of OpenText Content Server.

Examples include (but are not limited to):

  • NGINX Plus

  • KONG API Gateway

  • Other enterprise-grade API gateways

Such a component can:

  • Observe requests at ingress and egress

  • Measure full request lifecycle duration

  • Capture real user traffic

  • Expose detailed performance metrics

With appropriate plugins or modules, these metrics can then be:

  • Exported as Prometheus-compatible metrics

  • Processed by OpenTelemetry

  • Stored and visualized using existing backend components

This approach enables true end-to-end performance visibility, from the moment a request enters the system until it leaves.

Summary

The POC demonstrates that meaningful performance data can be extracted from xECM using agentless techniques, primarily through log analysis. However:

  • Log-based and API-based approaches are inherently partial

  • Full system performance visibility cannot be achieved without observing real request flow

Recommended strategy:

  • Use the POC’s log-based and API-based metrics for targeted analysis and diagnostics

  • Introduce a reverse proxy or API gateway for complete, end-to-end performance monitoring

  • Combine both approaches for maximum observability
