Monitoring Expansion : Monitoring other systems

Created by Bram Verkuijlen, last modified on dec 30, 2025

This section provides guidance on applying the Monitoring Expansion Proof of Concept (POC) beyond OpenText Content Management Server (xECM). While the POC was specifically designed and tested for OTCM, many of its components and principles can be adapted to other enterprise systems.

Background

The POC focused on OTCM due to its limited native observability and Windows-based architecture. Many modern enterprise systems, however, support agent-based instrumentation or provide standard observability endpoints.

OpenTelemetry, for example, offers Java, .NET, Python, and other agents that can automatically collect traces and metrics from supported applications. Using these agents can simplify integration and reduce reliance on log-based pipelines.
https://opentelemetry.io/docs/zero-code/

The POC demonstrates that even when agent-based monitoring is not feasible (as with OTCM), meaningful telemetry can still be extracted using:

  • Log scraping
    Fluent-bit

  • API polling
    API Metrics Collector

  • Host metrics collection
    Health Metrics Collector

  • Log-derived metrics
    Log Metrics Collector

These approaches are broadly applicable and can serve as a fallback when auto-instrumentation fails.

Recommended Approach

Agent-Based Monitoring

  1. Deploy native OpenTelemetry agents where supported:

    • Java Agent for Java-based applications

    • .NET Agent for .NET systems

    • Python / Node.js Agents for respective applications
      https://opentelemetry.io/docs/zero-code/

  1. Verify automatic instrumentation coverage:

    • Endpoints

    • Database queries

    • External API calls

  1. Integrate agent-collected telemetry into central collectors:

    • Prometheus-compatible metrics

    • OpenTelemetry trace data

    • Optional aggregation through Fluent Bit or similar tools

Benefits:

  • Minimal custom development

  • Standardized telemetry format

  • Easier long-term maintenance and upgrades

POC Collectors as Fallback

If auto-instrumentation is not feasible or does not provide sufficient coverage:

  1. Use the POC collectors to gather:

    • Log-based metrics (internal timings, system events)

    • API metrics (availability and basic performance)

    • Host/system metrics (CPU, memory, disk)

    • Derived metrics from logs

  1. Combine multiple collectors to reconstruct as much observability as possible:

    • Central Collector consolidates logs, metrics, and API data

    • Prometheus/Loki backends for storage and visualization

  1. Consider limitations:

    • Log quality impacts metric accuracy

    • API-based measurements reflect only collector-initiated requests

    • Full end-to-end traces require careful correlation of log events

This approach ensures that even hard-to-monitor applications can provide actionable performance and operational telemetry.

Capabilities and Limitations

Capability

Notes / Applicability

Agent-based metrics & traces

Full support if system allows OpenTelemetry agent instrumentation

Log-derived metrics

Available for most systems, but accuracy depends on log structure and detail

API metrics

Useful for endpoints that can be polled; limited by authentication and sampling

Host metrics

Supported via collectors on any host OS

Always try agent-based monitoring first. Use POC collectors as a fallback for applications with limited observability options or unsupported frameworks.

Summary

The Monitoring Expansion POC is broadly adaptable to other enterprise systems. The recommended strategy is:

  1. Start with agent-based monitoring for systems that support it

  2. Use POC collectors to supplement or replace missing telemetry

  3. Leverage centralized collectors and Prometheus/Loki to store, process, and visualize the data

  4. Combine approaches to maximize observability while minimizing development effort

By following this approach, organizations can gain meaningful insight into system performance and behavior even for applications that lack native observability support.
