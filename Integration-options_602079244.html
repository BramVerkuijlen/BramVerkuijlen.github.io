Monitoring Expansion : Integration options

Created by Bram Verkuijlen, last modified on dec 30, 2025

This section describes the possible integration paths between the Monitoring Expansion Proof of Concept (POC) and AMI (AmeXio Monitoring Insights).

The goal of this page is not to define a final integration design, but to document:

  • What integration options were identified during the internship

  • How each option would work at a high level

  • The advantages and trade-offs of each approach

Actual implementation are intentionally left out of scope.

Purpose

The Monitoring Expansion POC was designed to explore modern observability tooling (OpenTelemetry, Fluent Bit, Prometheus, Loki) in the context of enterprise ECM systems.

Because AMI is AmeXio’s existing monitoring platform, a natural follow-up question is:

How could the results of this POC be integrated into AMI?

Two realistic integration options were chosen.

Option 1 – Translation Layer into AMI

Overview

In this option, a small translation module would be built between the Central OpenTelemetry Collector and the AMI ingestion pipeline.

This module would:

  • Receive telemetry from the Central Collector

  • Transform it into formats and models supported by AMI

  • Forward the data into AMI’s existing processing and storage pipeline

The Monitoring Expansion POC remains the data acquisition layer, while AMI remains the central monitoring platform.

Conceptual Flow

  • Central OpenTelemetry Collector exports telemetry

  • Translation module maps OpenTelemetry data to AMI formats

  • AMI ingests telemetry as native data

This allows AMI to fully own the data once ingested.

Advantages

  • Full integration into the AMI ecosystem

  • Telemetry becomes usable by:

    • AMI dashboards

    • AMI alerting

    • AMI reporting and analytics

  • Centralized monitoring experience for operators

  • Long-term scalability and consistency

Trade-offs & Challenges

  • Requires development effort to:

    • Map OpenTelemetry data models to AMI models

    • Maintain compatibility as schemas evolve

  • Higher upfront complexity

  • Requires architectural alignment with AMI’s ingestion design

Suitability

This integration option is best suited for AmeXio if:

  • Long-term production use of observability data is a goal

  • Future proof evolution of AMI is planned

  • Investment in observability modernization is acceptable

  • Centralized ownership of monitoring data is required

This option is recommended when AMI is viewed as a long-term strategic observabillity platform rather than a visualization-only solution.

Option 2 – Shared Grafana Data Sources

Overview

In this option, no direct data integration into AMI is performed.

Instead:

  • The Grafana instance used by AMI is configured with additional data sources:

    • Prometheus (from the POC)

    • Loki (from the POC)

  • Dashboards can visualize POC telemetry alongside existing AMI telemetry

The Monitoring Expansion POC and AMI remain logically separate, but share a visualization layer.

Conceptual Flow

  • POC runs independently

  • Prometheus and Loki expose telemetry

  • AMI’s Grafana connects to these as additional data sources

  • Dashboards combine data from multiple systems

Advantages

  • Very low implementation effort

  • No changes required to AMI backend systems

  • Fast validation of observability value

  • Ideal for demos, research, and internal evaluation

Trade-offs & Limitations

  • Telemetry is not ingested into AMI

  • Data cannot be used by:

    • AMI alerting

    • AMI automation

    • AMI analytics pipelines

  • Monitoring remains partially fragmented

Suitability

This integration option is best suited for AmeXio if:

  • Quick visualization is the primary goal

  • No changes to the AMI backend are desired

  • The integration is exploratory or temporary

This option is not recommended for long-term production use, as the telemetry data cannot be reused within the broader AMI ecosystem (e.g. alerting, correlation, or downstream analytics). It should be viewed as a low-effort, low-impact integration path.

Recommended Approach

The two integration options are not mutually exclusive and can be adopted in phases.

For AmeXio, Option 2 (Shared Grafana Data Sources) is the most suitable starting point. It enables fast validation of the observability data produced by the POC, requires minimal effort, and carries low risk to existing AMI systems.

In parallel, Option 1 (Translation Layer into AMI) can be designed and developed as part of a broader AMI modernization or platform upgrade. This phased approach allows AmeXio to gain immediate value from the POC while working toward a fully integrated, future-proof observability architecture.

Notes

  • Both options intentionally keep AMI out of the critical path of the POC

  • The POC is designed to remain usable and valuable even without AMI integration

  • These integration paths are not mutually exclusive and could be phased
