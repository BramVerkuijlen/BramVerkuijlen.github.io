Monitoring Expansion : OpenText Content Server (xECM)

Created by Bram Verkuijlen, last modified on dec 18, 2025

This section documents OpenText Content Server (Extended ECM / xECM) V24.4 from a monitoring and observability perspective.

The goal of this part of the documentation is not to explain how xECM works functionally, but to describe:

  • What monitoring data xECM exposes

  • How that data can be accessed

  • What limitations exist

  • How xECM integrates into the observability Proof of Concept

This documentation is based on hands-on technical research performed during the internship project and reflects what is realistically achievable within enterprise xECM environments running on Windows.

Purpose

xECM is the primary monitored system in this Proof of Concept.

All logs, metrics, and derived traces originate from:

  • The Content Server itself

  • Its internal logging mechanisms

  • Its limited external monitoring interfaces

Because xECM does not support native OpenTelemetry agents or exporters, the observability pipeline is built around xECM rather than inside it.

Context

For this POC, OTCM is deployed as:

  • Version: OpenText Content Server V24.4

  • Operating System: Windows Server

  • Architecture: Monolithic Java-based application

All monitoring components (Fluent Bit, OpenTelemetry, Prometheus, Loki, Grafana) are deployed outside of OTCM and interact with it through:

  • File-based log access

  • Network-based endpoints

  • Periodic API polling

Key Responsibilities

Within the scope of this Proof of Concept, OpenText Content Management (OTCM) is responsible for generating all source data used by the observability pipeline.

OTCM itself does not act as a monitoring or observability platform. Instead, it exposes operational data indirectly through logs, internal monitoring events, and accessible API endpoints. These outputs form the foundation for all downstream observability processing.

The key responsibilities of OTCM in this POC are:

  • Generating application logs describing user actions, security events, request handling, and internal processing.

  • Producing performance-related logs, such as timing and thread execution information.

  • Emitting system monitoring events through a native monitoring endpoint.

  • Exposing basic REST API endpoints that can be used for availability and performance checks.

  • Acting as the business-critical workload whose behavior and health are being observed.

OTCM does not perform:

  • Metric aggregation

  • Trace generation

  • External data export using observability standards (e.g. OTLP)

  • Agent-based instrumentation

All processing, enrichment, and transformation of data occurs outside of OTCM.

Architecture Role

In the overall architecture of the POC, OTCM functions as the origin of all observability data.

Because OTCM does not natively support modern observability standards, it is treated as a black-box enterprise application. Observability is achieved by extracting data from the outside rather than instrumenting the application internally.

High-level architectural role of OTCM:

  • Source system for logs, events, and operational signals

  • Uninstrumented application, requiring log-based and indirect monitoring approaches

  • Upstream dependency for all other monitoring components

Conceptually, OTCM sits at the start of the data flow.

This architectural position strongly influenced the technical choices made in the POC, particularly:

  • The decision to use Fluent Bit for log ingestion

  • The reliance on OpenTelemetry Collectors for normalization and enrichment

  • The focus on log-derived metrics

Limitations and Constraints

The following constraints of OTCM are central to this project and explain many of the architectural decisions:

  • OTCM does not support native OpenTelemetry instrumentation

  • Java agent-based monitoring is not feasible in typical OTCM deployments on Windows

  • No native push mechanism exists for metrics or traces

  • Observability data must be collected via:

    • File-based log scraping

    • Native system monitoring events

    • External API polling
