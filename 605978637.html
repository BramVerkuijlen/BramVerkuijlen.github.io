Purpose / Overview

System Monitoring Events capture system-level status, configuration, and operational events within OpenText Content Server (OTCM).

These events are configurable via the Admin Server:

Admin Server → System Monitoring → System Monitoring

From this interface, administrators can enable or disable specific categories of system events, allowing control over:

  • Which subsystems generate monitoring events

  • The scope and verbosity of emitted events

  • Noise reduction in production environments

This makes System Monitoring Events selectively tunable, unlike most file-based logs which are always written once enabled.

Unlike request-based logs (Thread, Timing, Web Client), these events focus on health, stability, and background processing, not on individual user requests or execution timing.

They record events such as:

  • JVM crashes and fatal errors (e.g. hs_err_xxx.log)

  • Admin Server lifecycle events

  • Cache purges (File Cache, KINI Settings Cache)

  • Memcached connectivity or failures

  • Search / Federator errors

  • DCS (Document Conversion) failures

  • IPool Quarantine events

  • Database-level SQL errors

  • Distributed Agent long-running tasks

  • Backup status and disk-space warnings

  • WebReports execution failures

  • Certificate expiry checks

  • Memory usage warnings

These events are event-driven, emitted when something noteworthy happens in the system.

Field

Description / Metric

level

eventType

High-level classification of the event

message

Human-readable description of the issue or action

componentCode

Component generating the event (e.g. systemMonitor)

Service identifier (e.g. xecm)

applicationID

Application or subsystem identifier

applicationVersion

OTCM version

server

Server name and port

thread

Thread number where the event occurred

logger

Logging source or class

These events intentionally do not include execution duration, SQL timing, or request-level metrics.

Relevance

System Monitoring Events are primarily useful for platform health monitoring and alerting, rather than request-level troubleshooting.

Correlation

System Monitoring Events are especially useful when correlated with:

  • Thread Logs – identify backend execution context around failures
    Thread Logs

  • Thread Summary Timing Logs – detect whether system events coincide with latency spikes
    Thread Summary Timing Logs

  • SQL Connect Logs – correlate database-level errors or connectivity issues
    SQL Connect Logs

  • Web Server Client Logs – identify user-facing failures that triggered system events
    Web Server Client Logs

Correlation is typically time-based, not request-ID–based.

Observability Context

  • Best suited for alerting, health dashboards, and SRE-style monitoring

  • Low-to-medium volume, but high signal

  • Ideal candidates for:

    • Alerts (CRITICAL / SEVERE)

    • Incident timelines

    • Root cause analysis

  "applicationID": "-",
  "applicationVersion": "24.4",

  "logger": "-",
  "message": "WebReports run failed on DataID: 1078926",
  "server": "Opentext-xECM-f:2099",
  "serviceCode": "xecm",
  "thread": 4001,
  "utc_timestamp": "2025-12-19T09:02:49.000000Z"
}
